# AI 활용 문서 — 「Dice Orbit」 개발 워크플로우

## 출발점: AI가 못 하는 것부터 헤아렸다

우리 팀은 Unity 턴제 로그라이크 「Dice Orbit」을 8개월 동안 개발하면서 Claude Code(Anthropic의 터미널 기반 AI 코딩 에이전트, Claude Opus 모델)를 썼습니다. Unity 에디터 연동(MCP)을 붙여 씬과 프리팹 배선 같은 에디터 작업까지 AI에게 맡겼습니다. 다만 워크플로우를 설계할 때 기준으로 삼은 것은 AI가 무엇을 잘하느냐가 아니라 무엇을 못 하느냐였습니다. AI는 게임을 직접 실행해 보지 못합니다. 그래서 치명적인 런타임 오류를 스스로 확인할 수 없습니다. 재미가 있는지 없는지도 판단하지 못하며 세션이 끝나면 나눴던 맥락을 잊습니다. 이 세 가지 한계를 인정하고 나니 결론은 하나였습니다. AI를 자유롭게 풀어두는 대신, 사람의 판단과 검증이 단계마다 박혀 있는 파이프라인 위에 올려놓아야 한다는 것입니다.

## 다섯 단계 파이프라인

모든 시스템 구현이 다섯 단계를 거쳤습니다. "바로 코드부터"는 금지였습니다.

**1. 구현할 시스템 결정 — 사람.** 무엇을 만들 것인가는 기획의 영역입니다. 구현할 시스템은 작업자끼리 정했고 AI는 이 단계에 관여하지 않았습니다.

**2. 구조 토론 — 사람과 AI.** 각 작업자가 세부 구현을 맡아 AI와 일문일답으로 토론했습니다. AI가 기존 코드베이스를 먼저 탐색해 지금 구조를 파악한 뒤 설계 대안 두세 개를 장단점과 함께 내놓으면, 작업자가 하나를 고르거나 절충안을 지시했습니다.

**3. 설계 문서 — AI가 쓰고 사람이 고쳤다.** 토론이 끝나면 AI에게 설계(스펙) 문서를 쓰게 했습니다. 문서에서 고칠 부분을 짚어 수정시킨 뒤에야 확정했습니다. 이렇게 확정된 설계 문서가 날짜별로 21건 쌓였습니다.

**4. 구현 계획 — 코드가 되기 전에 걸러냈다.** 확정된 설계를 여러 단계로 쪼갠 구현 계획을 다시 AI에게 쓰게 했습니다. 비효율적으로 보이거나 문제가 될 만한 부분은 코드가 되기 전, 문서 단계에서 작업자가 짚어 고쳤습니다. 단계마다 "여기까지 끝나면 무엇이 동작해야 하는가"를 적어 중간 검증 지점을 만들었습니다. 이런 계획 문서가 18건 남아 있습니다.

**5. 구현과 검증 루프 — AI가 만들고 사람이 돌려봤다.** 계획 순서대로 AI가 구현했습니다. 다만 중간 단계마다 작업자가 직접 컴파일하고 실행해서 버그를 가려냈습니다. 발견한 버그는 증상을 전달해 원인부터 규명하게 한 뒤 고치게 했습니다. 추측 수정은 허용하지 않았습니다. 검증이 끝난 단위로만 커밋했고 기능 단위 브랜치와 PR로 나눠 언제든 되돌릴 수 있게 했습니다.

## 파이프라인이 작동한 세 장면

**주사위 덱 시스템 — 전 과정을 통과한 사례.** 설계 스펙(3단계 분할)에서 출발해 단계별 구현 계획을 거쳐 구현과 검증까지 마쳤습니다. 완성한 뒤에는 "현재 어떻게 동작하는가"를 담은 시스템 문서로 다시 정리했습니다. 설계 당시의 기록과 현재 구조 문서를 분리해 두면, 나중에 합류한 사람도 지금 상태를 바로 파악할 수 있습니다.

**완성된 기능을 버린 날 — 최종 판단은 사람.** '필요할 때 주사위를 하나씩 굴리는' 대체 시스템은 설계부터 구현까지 다 끝냈습니다. 그런데 플레이해 보니 게임의 감각과 맞지 않았습니다. 통째로 반려하고 main에 합치지 않은 채 브랜치에만 보존했습니다. 타일 속성을 3D 오브젝트로 표현하자는 설계안도 검토 끝에 채택하지 않았습니다. 더 단순한 말풍선 방식이 낫다고 봤기 때문입니다. AI가 만들었어도 재미없으면 버린다는 원칙이 실제로 지켜진 장면입니다.

**사람만 잡을 수 있었던 버그.** 캐릭터 표시명을 'Mage'에서 '마법사'로 바꾼 직후, 실행 검증에서 캐릭터 모집 화면의 카드가 엉뚱한 대체 이미지로 나오는 것을 발견했습니다. 증상을 전달하자 AI가 원인을 찾아냈습니다. 카드가 표시명을 스프라이트 매핑 키로 쓰고 있어서 이름을 바꾸는 순간 매칭이 깨진 것이었습니다. AI는 실행해 보기 전까지 이 버그를 알 길이 없었습니다. 단계마다 사람이 돌려보는 루프가 필수인 이유입니다.

## 숫자로 남은 결과

2026년 1월부터 8월까지 커밋 698건을 쌓았습니다. 설계 스펙 21건과 구현 계획 18건이 저장소에 날짜별로 남아 있고 기능 단위 브랜치는 20개가 넘습니다. 문서 인덱스에는 설계 기록마다 상태를 적었습니다. 구현됨, 완료, 미채택, 대체됨. AI가 쓴 문서라도 낡으면 폐기 표시를 해서 그때의 계획과 지금의 구조를 혼동하지 않게 했습니다.

## 맺으며

돌아보면 AI 활용의 핵심은 코드를 대신 짜게 하는 것이 아니었습니다. 토론, 설계, 계획, 구현, 검증으로 이어지는 파이프라인 위에 AI를 올려놓고 판단이 필요한 자리마다 사람을 세워 두는 것이었습니다. 문서를 코드보다 먼저 쓰게 하니 산출물의 품질을 구현 전에 걸러낼 수 있었습니다. 실행 검증을 사람이 쥐고 있으니 AI가 볼 수 없는 오류와 게임성 문제를 놓치지 않았습니다.
